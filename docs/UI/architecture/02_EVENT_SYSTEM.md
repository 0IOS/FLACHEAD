# FLACHEAD UI — Event System Specification

## 1. Purpose

This document defines the communication system between FLACHEAD components.

FLACHEAD contains many independent systems:

* UI screens
* playback engine
* input manager
* hardware managers
* library services
* background workers

A centralized event system allows these components to communicate without creating tight dependencies.

Primary principle:

> Components should communicate through events, not direct connections.

---

# 2. Design goals

The event system must be:

* lightweight
* asynchronous
* predictable
* debuggable
* optimized for Raspberry Pi Zero W

---

# 3. Event architecture

Data flow:

```text id="x7m4q9"
Component

↓

Event Dispatcher

↓

Event Queue

↓

Subscribers

↓

Component Response
```

---

Example:

```text id="m5x8q3"
Playback Engine

Track Changed Event

↓

Mini Player

↓

Update Track Information
```

---

# 4. Event categories

FLACHEAD events are divided into:

```text id="v8m3x5"
1. Input Events

2. Playback Events

3. UI Events

4. Hardware Events

5. Storage Events

6. System Events
```


# 10. Event structure

Every event contains:

```text id="u5m3x9"
Event

├── Type

├── Source

├── Timestamp

├── Data

└── Priority
```

---

Example:

```text id="k8m4x5"
TRACK_CHANGED

Source:

Playback Engine

Data:

Track ID: 52
```

---

# 12. Event queue

The event queue handles:

* ordering
* priority
* delivery

---

Architecture:

```text id="d8m4x6"
Event Queue

├── Incoming Events

├── Priority Sort

├── Dispatch

└── Cleanup
```

---

# 13. Threading model

Recommended:

```text id="m5x8q3"
Audio Thread

↓

Event Queue

↓

UI Thread
```

---

Audio thread must not:

* wait for UI
* block on events

---

# 14. Event filtering

Repeated events should be filtered.

Example:

Volume dial:

Bad:

```text id="v8m3x5"
100 events/sec
```

---

Good:

```text id="c6m4x9"
Smooth grouped updates
```

---

# 15. Event logging

Debug mode:

Can record:

* event type
* timestamp
* source

---

Example:

```text id="r7m3x8"
15:02:41

TRACK_CHANGED

Playback Engine
```

---

Must be disabled or limited in production.

---

# 16. Error handling

Unknown event:

Ignore safely.

---

Invalid event:

Log warning.

---

Event queue overflow:

Discard low-priority events first.

---

# 17. Performance requirements

Event processing:

Target:

```text id="n8m4x6"
<5ms
```

---

Must not:

* block rendering
* interrupt audio
* consume excessive memory

---

# 18. Acceptance criteria

Implementation is complete when:

* components communicate through events
* event priority works
* playback remains independent
* debugging is possible
* no tight coupling exists

---

# 19. Architectural recommendations

Required module:

```text id="w5m3x7"
Event Manager

├── Event Definition

├── Queue

├── Dispatcher

├── Subscriber Registry

└── Logger
```

---

# 20. Implementation notes for AI coding agent

When implementing:

* Avoid direct callbacks between major systems.
* Use typed events.
* Keep event names consistent.
* Separate critical and background events.
* Design for future applications and plugins.

The event system is the communication backbone of FLACHEAD. A clean event architecture prevents the project from becoming impossible to maintain as features expand.
